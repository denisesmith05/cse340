const processAssignCategoriesForm = async (req, res) => {
    const projectId = req.params.projectId;

Here's what each part does:

req.params.projectId gets the project's ID from the URL.

req.body.categoryIds gets the category IDs submitted through the form.

Array.isArray() handles the difference between a single selected category and multiple selected categories. A single selection may arrive as a string, while multiple selections may arrive as an array.

await updateCategoryAssignments(...) waits for the database update to finish before moving on.

req.flash('success', ...) stores a temporary success message in the session, assuming flash middleware is configured.

res.redirect(...) sends the browser to the project's page.

One important detail: the flash message is generally retrieved on the next request and displayed in the rendered page. This is useful because the user can see confirmation after the redirect.

You're right that redirecting takes the user back to the project page without requiring them to find another link manually.

There's another important benefit called the Post/Redirect/Get (PRG) pattern:

POST: The user submits the form, and the server updates the category assignments.

Redirect: The server redirects the browser to the project page.

GET: The browser requests the project page and displays the updated information and success message.

This pattern also helps prevent accidental duplicate submissions if the user refreshes the page after submitting the form.

const organizationValidation = [
    body('name')
        .trim()

Here's how your rules work:

body('name') selects the submitted name field from the request body.

.trim() removes whitespace from the beginning and end.

.notEmpty() checks that the field isn't empty.

.isLength({ min: 3, max: 150 }) enforces the allowed name length.

.normalizeEmail() normalizes the email address.

.isEmail() checks whether the value has a valid email format.

.withMessage() provides a helpful error message when its associated validation rule fails.

Your description validation also limits the description to 500 characters.

One important detail: defining these validation rules doesn't automatically stop your controller from running when validation fails. Your application also needs middleware or controller logic that checks the validation results and responds appropriately.

Let's reflect on your approach
Denise, why is it important to validate information on the server even though your EJS form already uses HTML attributes like required, maxlength, and type="email"?

I feel like these html attributes deal more with the front-end validation while the validating on the server basis is dealing more with back-end
Exactly, Denise! You've identified the key distinction between front-end and back-end validation. Great job! 😊

You're right that HTML attributes handle validation on the front end, while your organizationValidation rules handle validation on the back end.

Here's why that distinction matters:

Front-end validation: Gives users immediate feedback in their browser. For example, required can prevent a form from being submitted when a field is empty.

Server-side validation: Checks the data when it reaches your server, even if someone bypasses or disables the browser's validation.

Together: They improve the user experience while helping protect your application's data integrity.

For example, someone could open their browser's developer tools, remove the required attribute, and submit an empty organization name. Your server-side validation should catch that empty value before the application saves it.

One final detail: your validation rules define what to check, but your application must also inspect the validation results and handle errors before saving the data.
