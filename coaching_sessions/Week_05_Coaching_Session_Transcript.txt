const processUserRegistrationForm = async (req, res) => {
    const { name, email, password } = req.body;

    try {
        const salt = await bcrypt.genSalt(10);
        const passwordHash = await bcrypt.hash(password, salt);

        await createUser(name, email, passwordHash);

        req.flash('success', 'Registration successful! Please log in.');
        res.redirect('/');
    } catch (error) {
        console.error('Error registering user:', error);
        req.flash('error', 'An error occurred during registration. Please try again.');
        res.redirect('/register');
    }
};


I chose bcrypt because it hashes passwords with a salt, making stored hashes harder to crack if the database is exposed. createUser receives and stores the hash—not the original password.
Assistant:
Excellent, Denise! You've explained both what the code does and why you chose bcrypt. Let's reinforce a couple of important concepts from your implementation.
- bcrypt.genSalt(10) generates a random salt, with 10 specifying the work factor.
- bcrypt.hash(password, salt) uses that salt to create the password hash.
- await createUser(name, email, passwordHash) waits for the database operation to complete before showing the success message and redirecting the user.
One additional security consideration is that your try...catch handles errors, but you'll also want to validate the submitted fields and handle duplicate email addresses appropriately.
Why do you think bcrypt uses a salt when hashing a password instead of simply hashing the password by itself?
Denise (User):
A salt makes each password hash unique, even when two users choose the same password. That prevents attackers from recognizing matching hashes and makes precomputed lookup tables (such as rainbow tables) far less useful. bcrypt stores the salt with the hash, so it can use that same salt to verify a password at login.
Assistant:
Exactly right, Denise! You've identified the key security benefits of salting passwords.

Topic 3 — Protected Access Middleware
Denise (User):
const requireRole = (role) => {
    return (req, res, next) => {
        if (!req.session?.user) {
            req.flash('error', 'You must be logged in to access this page.');
            return res.redirect('/login');
        }

        if (req.session.user.role_name !== role) {
            req.flash('error', 'You do not have permission to access this page.');
            return res.redirect('/dashboard');
        }

        next();
    };
};

const requireLogin = (req, res, next) => {
    if (!req.session?.user) {
        req.flash('error', 'You must be logged in to access that page.');
        return res.redirect('/login');
    }

    next();
};


requireLogin checks whether a user is in the session. If not, it flashes an error and redirects to login; otherwise, next() lets the request continue.
requireRole(role) first requires a logged-in user, then compares the session user’s role_name with the required role. Missing authentication redirects to login; a wrong role gets an error message and is redirected to the dashboard. If both checks pass, next() proceeds to the route handler.
Assistant:
Great explanation, Denise! You've clearly identified the difference between authentication and authorization.
- requireLogin checks authentication: has the user logged in?
- requireRole(role) checks authorization: does the logged-in user have the required role?
- next() passes control to the next middleware or route handler when the checks succeed.
- return res.redirect(...) stops the middleware from continuing after a failed check.
I also like that your requireRole middleware checks for a logged-in user before checking their role. That prevents the application from trying to authorize someone who hasn't authenticated.
One security principle worth remembering is that hiding a link in the interface isn't enough to protect a route. A user could manually type a URL into their browser, so the server-side middleware must enforce the restriction.
